ID / locationR1 — src/PluginProcessor.cpp:1199, “Adopted snapshots can miss first save”
ClaimAdoption finishing after programMailbox.take() but before generation loads makes the save select its old snapshot, combining current sound with stale metadata.
Trigger / orderClaimed interleaving between mailbox consumption, adoption completion and generation load.
Root causeNone — the machinery does not exist. programMailbox, applyResolved, Mailbox and take() have zero occurrences in src/ or tests/. Line 1199 is inside a comment block. There is no program state machine to hold a mailbox: getNumPrograms()→1, getCurrentProgram()→0, setCurrentProgram(int) empty.
Analogue checkedWrong names are not a disproof, so the equivalent mechanism was traced. The save path does have exactly one staged-vs-published selection: getStateInformation’s ADAPTIVE block choosing on engine.adaptiveRestorePending(). It is sound for two independent reasons. (1) Ordered: the stager writes the three staged mirrors and then sets adaptivePending with release; the reader loads it with acquire before reading them, so seeing the flag implies seeing the values. (2) Never consumed: the audio thread’s exchange(false) clears only the flag — the mirrors persist until the next setStateInformation. So the interleaving resolves the same way either way: flag up ⇒ mirrors hold the loaded truth; flag down ⇒ the engine already applied those same values. There is only ever one generation in flight.

G1 — C6385 · production · FIXED

Scanner / rulePREfast · C6385 (reading invalid data)
Locationsrc/dsp/AnabasisEngine.cpp:882:9 — 1 finding
Message“Reading invalid data from 'gains': the readable size is '8' bytes, but '-4' bytes may be read.”
Root causegrMinThisCall = jmin(grMinThisCall, gains[0], gains[nCh - 1]) is the only indexed read of gains outside a ch < nCh loop. gains is float[kMaxChannels] = 8 bytes; the -4 in the message is PREfast deriving nCh == 0, i.e. gains[-1]. The bound is real but is established in the caller: process() returns false on numChannels <= 0 before any chunk runs, and processChunk has exactly one call site, inside process() after that guard. PREfast analyses each function alone and cannot carry the precondition across.
Affected surfaceProduction DSP, audio thread.
RiskLow today, structurally fragile. No reachable defect on current code — the guard is unconditional. But correctness depends on a precondition ~640 lines away in another function, with nothing local enforcing it: a second caller for processChunk, or any weakening of the process() guard, turns this into a genuine out-of-bounds stack read on the audio path. It is also the only production finding, so leaving it trains reviewers to skip the production scanner surface entirely.
Benefit of fixingRemoves the sole production finding; makes the bound provable where it is used; eliminates a latent regression trap.
Cost / complexityMinimal. One clamped local. No allocation, no lock, no branch that survives the optimiser, no behaviour change for any nCh >= 1. Realtime guarantees untouched.
Needs fix?SHOULD FIX — false positive against today’s code, genuine as a maintainability and regression hazard.
Worth fixing now?Yes. Cost is one line; risk of the fix is nil; risk of leaving it grows silently with every future edit to the call graph.
DispositionFIXED — const int lastCh = juce::jmax (0, nCh - 1);
RoadmapNow — immediate. Shipped in this change.
PrecedentThe kMaxChannels third term on nCh was added for exactly this reason and carries a comment forbidding its removal as “redundant”: it is the term that makes the access provably in bounds. This fix applies the same rule to the lower bound.
BlockerNone.
StatusCLOSED — scanner-confirmed. PREfast run 33801797950 (a7112c4): 153 → 152 results, the delta being exactly this finding. No new finding introduced. src/ now reports 0.

G3 — C28182 ×8 + C6011 ×1 · tests · FALSE POSITIVE

Scanner / rulesPREfast · C28182, C6011 (dereferencing NULL pointer)
Locationtests/state_tests.cpp — 9 findings across the recursive component-tree walkers (findButtonByText, countSliders, collectTooltipless, collectUnfocusable and siblings)
Message shape“Dereferencing NULL pointer. 'c' contains the same NULL value as 'b' did.”
Root causeAnalyzer modelling error. The pattern is if (auto* b = dynamic_cast<T*>(c); b != nullptr && …) … followed by a recursive call on *c. PREfast treats dynamic_cast as identity, so it infers b == nullptr ⟹ c == nullptr and flags the recursion. A failed dynamic_cast says nothing about its operand, and Component::getChildren() never yields a null element.
RiskNone. The inference is unsound; there is no defect.
Cost of “fixing”Would require inserting if (c == nullptr) continue; guards against a condition JUCE cannot produce — defensive noise added to satisfy a wrong inference, in test code.
Needs fix?FALSE POSITIVE — DO NOT FIX
Worth fixing now?No, and not later either. Recorded so the next audit does not re-triage it.
RoadmapMonitor — no current action.

G4 — C28252 ×4 · tests · FIXED (round 2)

Scanner / rulePREfast · C28252 (inconsistent SAL annotation)
Locationtests/AllocationGuard.h lines 355, 363, 503, 511
Message“Inconsistent annotation for 'new': return/function has SAL_success(return!=0) on the prior instance.”
Root causeGenuine mismatch, not a false positive. All four sites are the nothrow operator new / operator new[] overloads, annotated ANABASIS_GUARD_RET_MAYBENULL (_Ret_maybenull_ _Post_writable_byte_size_). That contradicts the annotation the MSVC CRT already carries on its own prior declaration of the same operators. The repository’s annotation is arguably the semantically correct one — nothrow new does return null on failure — but two declarations of one function disagree, and PREfast is right to say so.
RiskNone at runtime. SAL is analysis-only and the macros expand to nothing off MSVC. Test-support header; never shipped. The cost is analytical: contradictory annotations degrade PREfast’s reasoning about allocation in the test suite.
Benefit of fixingModerate-low: 4 diagnostics, and restored analyzer fidelity on the allocation guard — which is the harness the realtime no-allocation proof depends on.
Cost / complexityLow edit, awkward verification. The likely fix is to drop the annotation on the nothrow overloads and let the CRT’s stand. But the exact CRT annotation cannot be read from this environment (no MSVC headers), so the fix is a hypothesis that only a Windows CI round can confirm — and a wrong guess is churn that leaves the diagnostic in place.
Needs fix?SHOULD FIX — DONE
What located itAn exact one-to-one correlation. The four findings are the four ANABASIS_GUARD_RET_MAYBENULL uses; the four ANABASIS_GUARD_RET_NOTNULL uses are clean. That split put the fault in the macro rather than in any individual overload — and explains the count, since only half the eight annotated operators could contradict anything.
FixThe diagnostic names the missing clause itself: the prior instance has SAL_success(return!=0). MSVC’s <vcruntime_new.h> declares the nothrow operators _Ret_maybenull_ _Success_(return != NULL) _Post_writable_byte_size_(_Size), and declares the throwing forms with no _Success_ at all — a throwing new returns or throws, it never fails by returning. The macro carried _Ret_maybenull_ and _Post_writable_byte_size_ but not _Success_. Added it: #define ANABASIS_GUARD_RET_MAYBENULL(sz) _Ret_maybenull_ _Success_(return != 0) _Post_writable_byte_size_(sz)

This aligns with the CRT contract rather than removing an annotation. The tempting alternative — dropping _Ret_maybenull_ — would have been the wrong repair: nothrow new genuinely can return null, and modelling that is the one thing this guard exists for. PREfast is not weakened.
DispositionFIXED — pending Windows PREfast confirmation, which is the authority here since the CRT headers cannot be read from this environment.
RoadmapNow — done in this round.
BlockerNone.
