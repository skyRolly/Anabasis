# Worklog — the JUCE 9.0.0 → 9.0.1 bump (2026-08-16)

Session-local evidence trail for **ADR-0028** and version 0.1.5. Raw investigation material, NOT
architecture documentation — `docs/SOURCE_OF_TRUTH.md`: worklogs are never cited as policy. The ADR
is the record of authority; this file is what it was derived from, plus the alternatives that were
rejected and why.

---

## Method: the delta was diffed, not read

The upstream release notes are a summary, and `DEPENDENCY_POLICY.md` upgrade rule 7 is explicitly
about the reasoning that breaks *without* a call site changing. So the first step was to put both
trees side by side rather than to read `CHANGE_LIST.md`:

```
$ git ls-remote --tags https://github.com/juce-framework/JUCE.git | tail -2
f8f8864172464b9adf9eba6101e1f784838d1597  refs/tags/9.0.0
e18f7f506c0b96f2c738a0bcd7fe6467a5005ad8  refs/tags/9.0.1

$ git fetch --depth=200 origin e18f7f50…      # into the existing build/_deps/juce-src
$ git diff --stat f8f8864 e18f7f5             # 199 files, +10500 −19561
```

The large deletion count is almost entirely `examples/Plugins/WebViewPluginDemoGUI/package-lock.json`
being regenerated (−21 857 lines there alone). Nothing in `examples/` or `extras/` is compiled by
this project.

### The reduction that carries the ADR

```
$ git diff f8f8864 e18f7f5 -- \
      modules/juce_dsp modules/juce_audio_basics modules/juce_audio_processors \
      modules/juce_data_structures modules/juce_audio_utils modules/juce_audio_plugin_client \
  | grep '^[-+][^-+]'
-  version:            9.0.0
+  version:            9.0.1          (× 6)
```

Six module-declaration strings, nothing else. That is the whole audio path, the whole parameter
system and both format wrappers — so "no audible change" stops being a hope and becomes a property
of the source. Every other verification below is confirmation of a conclusion the diff already
forces, which is the right order to do them in.

### The rule-7 register, answered by `git diff` rather than by re-reading

```
for f in juce_PopupMenu.cpp juce_ComboBox.cpp juce_TextEditor.cpp juce_Component.cpp \
         juce_MouseInputSource.cpp juce_ModalComponentManager.cpp juce_TooltipWindow.cpp \
         juce_Button.cpp juce_LookAndFeel_V2.cpp juce_LookAndFeel_V4.cpp \
         juce_RangedAudioParameter.cpp juce_AudioParameterFloat.cpp \
         juce_AudioProcessorValueTreeState.cpp juce_AudioProcessorEditor.cpp \
         juce_NormalisableRange.h juce_SIMDRegister_Impl.h; do
    echo "$(git diff --name-only f8f8864 e18f7f5 -- "**/$f" | wc -l)  $f"
done
```

All sixteen returned **0**. Those files back every row of the `DEPENDENCY_POLICY.md` rule-7 register
*and* every `juce_*.cpp:line` citation in `src/` and `docs/` (`LookAndFeel.h:222-225`,
`PluginParameters.cpp:145,160,172`, `POSTMORTEMS.md:90`, `DOCUMENTATION_COVERAGE.md:1041-1042`,
`KNOWN_ISSUES.md:680`, `ADR-0024:50,52,67,81`). A register walk usually means re-reading prose and
hoping; here it is a mechanical fact.

The one near miss: `juce_gui_basics/detail/juce_MouseInputSourceImpl.h` **did** change. Read in
full — the diff is 14 lines and touches `getTargetForGesture` only, dividing the peer position by
`getDesktopScaleFactor()` before the hit test. `setComponentUnderMouse`, which the `isMouseOver`
row turns on, is untouched. Had that been the changed function, the hover/tooltip row would have
needed re-deriving rather than re-confirming.

## What was found by reading, and would have been missed by trusting the notes

`CHANGE_LIST.md` for 9.0.1 lists seven headline items. Two things that matter to this project are
in neither that file nor `BREAKING_CHANGES.md`:

1. **`XmlDocument::readChildElements` now skips `<? … ?>` inside a character block.** This is the
   only change in the entire delta that touches data this product writes and reads. It is a
   widening (no producer here emits a processing instruction inside an element), which is why it is
   not a Serialization Registry change — but it is exactly the kind of thing that gets discovered
   later, from a bug report, if the diff is not read.
2. **The Linux vblank timer compared milliseconds with hertz.** Listed upstream as "Fixed a bug
   setting the vblank timer's interval". The one-line description does not convey that
   `getTimerInterval()` (ms) was compared against a refresh rate (Hz), so the guard could never
   agree and the timer that drives `dispatchDeferredRepaints` was restarted on every call.

## The KI-012 lead, and where it stops

Three 9.0.1 fixes land on the two branches KI-012's own "what would settle it" paragraph names.
The full reasoning is in the KI-012 addendum; what belongs here is the one thing that was
**measured** rather than read, and the reason nothing stronger was attempted.

Measured — the precondition of the `libXi.so` mechanism:

```
$ ./dlprobe                                  # with libxi-dev's symlink present
libXi.so     -> OPENED
libXi.so.6   -> OPENED
$ mv /usr/lib/x86_64-linux-gnu/libXi.so /root/libXi.so.hidden   # end-user machine
$ ./dlprobe
libXi.so     -> libXi.so: cannot open shared object file: No such file or directory
libXi.so.6   -> OPENED
```

So JUCE 9.0.0's `DynamicLibrary xinputLib { "libXi.so" }` fails on any machine without the `-dev`
package, and because `X11Symbols`' stubs return default-constructed values while X11's `Success` is
`0`, `setupXI2`'s error check passes against a library that never loaded. That chain is read from
the source; only the `dlopen` asymmetry above was executed.

**What was NOT done, deliberately.** The decisive experiment would be to hide the symlink, host the
built VST3 under `Xvfb`, inject XTEST pointer events and observe whether a control moves — the
harness from `2026-08-10-linux-editor-input-probe.md`, run twice, once per pin. It was not run, for
two reasons worth stating rather than leaving as an omission: it is a *reproduction* of a report
this repository has never reproduced, and building the harness is a larger piece of work than the
bump it would be attached to. The consequence is recorded honestly in the ADR and in KI-012 — three
candidate mechanisms closed, **no claim that the report is fixed**. If the report recurs at 0.1.5,
that experiment is the next step and this paragraph is the design for it.

## Verification, and the one that mattered

Same source, same project version (0.1.5), one variable changed — the baseline was rebuilt at 9.0.0
*after* the version bump so the pin was the only difference between the two trees.

| Check | Result |
|---|---|
| Configure + build, all targets, fresh tree | clean; no compiler diagnostic at either pin (the only `warning:` lines in both logs are `lto-wrapper: using serial compilation of N LTRANS jobs`) |
| `AnabasisTests` + `AnabasisStateTests` | 296 + 845 = **1141 checks, 0 failures**; the two suites' combined stdout is **byte-identical** to the 9.0.0 run, the `comboFit 31 px` / `shortcutRow 5 px` layout advisories included |
| `AnabasisChannelProbe` on the built VST3 | **byte-identical** across 33 configurations — {48 kHz, 44.1 kHz} × {512, 64} × 8 parameter sets, plus the macro-with-editor scenario — at `L=%.9f R=%.9f` per channel |
| pluginval, strictness 10, both modes ×3, editor under xvfb | pass |
| valgrind memcheck, both suites, rebuilt unsanitized at the new pin | **0 errors from 0 contexts** each |
| Clang leg — build (incl. LTO'd `Anabasis_VST3`), warning gate, compile canary, both suites, probe | clean; **the Clang-LTO'd bundle agrees with the GCC one digit for digit** |
| `check-docs` / `check-portability` / `check-citations` (both bases) | clean |
| Third-party symbol probes (rule 6) | every §2 component present by the same symbol; every §4 exclusion still absent |

**The probe is the one that mattered**, and it is worth saying why the suites were not enough on
their own. `AnabasisStateTests` compiles the plugin sources into a console app: no LTO, no VST3
wrapper. `DEPENDENCY_POLICY.md` rule 2's whole concern is that "a JUCE change can move
DSP/latency/editor behaviour invisibly to the headless gate", and the console apps are that gate.
The probe loads the **shipped bundle** through `AudioPluginFormatManager`, so `host → wrapper →
processBlock → engine` is the real, LTO'd path — and it prints numbers rather than a verdict, so
"unchanged" is a diff of 33 lines of nine-decimal output instead of a pass/fail that a coarse
oracle could produce either way.

Two footnotes on the probe evidence:

- Its `--verbose` header dumps all 50 hosted parameters with ids and names, so the diff also covers
  the parameter surface as the *host* sees it, not as the registry snapshot describes it.
- The macro scenario constructs the editor, which is the only place in this verification where
  `juce_graphics` and `juce_gui_basics` — two of the nine modules that actually changed — execute.
  (Nine, not five, and the recount is worth recording: the first pass through the diff read the
  module list off the *files I had already opened* and missed `juce_audio_devices`,
  `juce_audio_formats`, `juce_audio_processors_headless` and `juce_opengl`. `git diff` per module,
  with the two `version:` lines subtracted, is the form that cannot be miscounted; every document
  now quotes the six UNCHANGED modules instead, because that is the half the conclusion rests on.)

## Rejected alternatives

- **Reconfiguring the existing `build/` tree instead of a fresh one.** Wrong, and silently so:
  `ANABASIS_JUCE_TAG` is a `CACHE STRING`, and `set(... CACHE ...)` does not overwrite an existing
  cache entry. A reconfigure keeps fetching `f8f8864…` and reports success. Verified by reading the
  old tree's `CMakeCache.txt` after the edit; noted in `BUILD.md` so the next person does not lose
  an afternoon to it.
- **Comparing the two builds' binaries.** Considered and dropped: LTO, `--gc-sections` and embedded
  build paths make byte-comparison of `libAnabasis_SharedCode.a` or the `.so` meaningless. The
  vendored `juce_graphics_lunasvg.c.o` differs by 656 bytes between the two trees purely because
  the build directory names differ in length. Behavioural comparison at the bundle boundary is the
  answer to the question the binary diff was trying to ask.
- **Bumping `scripts/setup-linux.sh` for the `libXi.so.6` change.** Not needed and would have been
  wrong: the change *reduces* what a machine needs (a SONAME instead of a `-dev` symlink), and the
  build dependencies are unchanged. `libxi-dev` is not in that script's explicit list anyway — it
  arrives transitively.
- **Recording the 9.0.1 fixes as a KI-012 closure.** Refused. See above.
